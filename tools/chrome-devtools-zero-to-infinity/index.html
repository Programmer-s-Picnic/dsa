1. What are Chrome Developer Tools?

Chrome Developer Tools, usually shortened to DevTools, is a collection of diagnostic and experimentation tools built into Chrome. It lets you look inside the webpage, the browser's document structure, applied styles, JavaScript execution, network requests, site storage, accessibility information and performance recordings.

Imagine a house: the webpage is the finished room you see, whereas DevTools lets you inspect the wiring, walls, dimensions and electrical signals. You can alter many things in your own browser to test an idea, but that does not normally change the live website for other people.

Browser page⇄DOM + CSS⇄JavaScript⇄HTTP/network⇄Server/API

Example: A button is visible but does nothing. Does it lack a click handler? Is JavaScript throwing an exception? Did an API call return 500? Is the button disabled by CSS or covered by another element? DevTools helps you distinguish these causes.

Safety: The Console can execute JavaScript as part of a website. Never paste commands from strangers, especially when logged in to email, banking or administration sites. DevTools is powerful; use code you understand on websites you control or trust.

3. Understand what DevTools is observing

HTML received from a server is parsed into a Document Object Model (DOM). CSS determines layout and appearance. JavaScript can change the DOM and interact with server APIs. HTTP requests fetch the HTML, CSS, scripts, images and data. The browser combines these pieces to draw pixels on the screen.

URL→DNS and network→HTTP response→DOM + CSS→Render

The View Page Source command shows the original HTML response; Elements shows the current DOM, which JavaScript may have changed. These are not always identical. The Network panel shows requests. Sources shows loaded code and debug controls. Console shows messages and lets you evaluate JavaScript in the page's execution context.

4. Elements panel: repair HTML and CSS

Use Elements when a button is misplaced, text looks strange, a card overflows, a hidden element remains visible, or CSS rules seem to be ignored. On the left is the DOM tree; on the right or below are tabs such as Styles, Computed, Layout, Event Listeners and Accessibility (available views depend on Chrome's layout).

DOM, selectors and the Styles pane

<div class="product-card" id="product-17">
  <h2>Apples</h2>
  <button class="buy-button">Buy</button>
</div>

The selector .product-card matches the class, #product-17 matches the ID, and button matches element names. A selector might appear several times in the Styles pane; CSS specificity, source order, cascade layers and !important can influence which value wins. Crossed-out declarations are not currently applied.

Computed styles, box model and layout

Computed shows the resulting styles after the cascade. The box model describes content, padding, border and margin. The Layout view can highlight CSS Grid or Flexbox, helping you diagnose item spacing and alignment. Test pseudo-classes such as :hover or :focus using :hov controls in Styles.

/* Example box-model calculation */
.card {
  width: 240px;
  padding: 20px;
  border: 2px solid steelblue;
}
/* With content-box sizing:
   overall width = 240 + 40 + 4 = 284px.
   With border-box sizing:
   total width remains 240px. */
Lab 2 — Fix an unreadable heading (5 minutes)
  1. In the playground, find the Lab A heading and pale-coloured sample text.
  2. Right-click the pale heading and choose Inspect.
  3. In Styles, locate .buggy-title and change color to #123b63.
  4. Disable a rule by unchecking it; enable it again. Open Computed and inspect the final colour.
  5. Reload the page. Observe that the temporary change normally disappears.

Expected: You can test a readable colour without changing the original website files. Keep the correct CSS value for a later real source-code edit.

Editing the DOM: useful, but temporary

Double-click text or HTML attributes in Elements to experiment. Right-click an element to edit its HTML or add a class. The results affect your browser's in-memory DOM, not the server-side source. If JavaScript rerenders that section, your manual changes can be overwritten even without reloading.

Advanced exercises: Force :hover on a navigation menu; identify the nearest positioned ancestor of an absolutely positioned element; inspect a z-index stacking problem; and use the Accessibility pane to read an element's computed accessible name and role.

5. Console: messages, errors and JavaScript experiments

The Console reports diagnostic messages, errors, warnings, some security warnings and the output of code you run manually. The Console is not the backend server's terminal; a Node.js console.log() executed on the server normally appears in server logs, not the website's browser Console.

2 + 3
"5" + 1
Number("5") + 1
document.title
document.querySelector("h1").textContent

console.log("Hello from Champuter");
console.warn("This is a warning");
console.error("This is an error");
console.table([{name:"Asha",marks:88},
               {name:"Ravi",marks:72}]);

For selected DOM elements, the DevTools-specific shortcut $0 usually refers to the currently inspected element. Try $0.textContent after inspecting a heading. The last evaluated result may be available as $_ in DevTools. These are Console convenience features, not ordinary JavaScript variables in every environment.

Lab 3 — See and classify Console output (5 minutes)
  1. Open the playground's Lab B section and the DevTools Console.
  2. Click Print log, warning, error and table.
  3. Compare the log, warning, error and formatted table.
  4. Click Cause a deliberate ReferenceError. Find its source link and click it.
  5. Use the Console filter or log-level controls to show only errors, then restore the view.

Expected: A deliberate ReferenceError is reported with a source location, while console.error() is an error-level message rather than necessarily an exception.

Console utilities worth learning

console.time("work");
// do some work
console.timeEnd("work");

console.group("Student report");
console.log("Asha", 88);
console.log("Ravi", 72);
console.groupEnd();

console.clear();

Try console.trace() to see a call stack. console.assert(condition, message) can log when a condition fails. Be careful when copying page objects or cookies: they may contain confidential information. Never use self-XSS bypass instructions from someone else simply to paste their code.

6. Sources panel: debug JavaScript properly

Use Sources when a click produces the wrong result, an event handler never runs, variables contain unexpected types, or JavaScript throws an exception. Instead of adding endless logs, pause execution and inspect the program at the point where the problem occurs.

Breakpoints and stepping controls

Open a JavaScript file from the left-hand file tree and click a line number to set a breakpoint. Run the action that reaches that line. The debugger pauses before executing the line. Inspect Scope, Watch and Call Stack; hover over variables. Use Resume (often F8), Step over (often F10), Step into (often F11) and Step out (often Shift + F11). Shortcuts may vary by OS or configuration.

Lab 4 — Find the string-addition bug (10 minutes)
  1. Open playground Lab C. The defaults are 5 and 1. Click Add the numbers; the page shows 51 instead of 6.
  2. Open Sources. Find playground.html and search for function calculateSumBug.
  3. Set a breakpoint on the statement const sum=a+b;, then click the button again.
  4. Inspect a, b, typeof a and typeof b in Scope or Watch.
  5. Predict the result of Number(a)+Number(b) in the Console while paused.
  6. Resume. Explain why string concatenation occurred.

Expected: HTML input .value returns strings. The operator + concatenates them. A suitable fix for valid numeric input is const sum=Number(a)+Number(b);, accompanied by input validation.

// Simplified corrected implementation
const a = Number(firstNumber.value);
const b = Number(secondNumber.value);
if (!Number.isFinite(a) || !Number.isFinite(b)) {
  throw new Error("Please enter valid numbers");
}
const sum = a + b;

7. Network panel: follow HTTP requests and API responses

The Network panel answers questions such as: Did the browser send the request? Which URL did it use? Did the server respond? What status code came back? What request headers or payload were sent? How long did DNS, connection, waiting and download take?

Open Network and reload the page. Typical columns include Name, Status, Type, Initiator, Size, Time and a waterfall timeline. Click a request to inspect Headers, Payload, Preview, Response, Initiator and Timing. A page can request HTML, CSS, JS, images, fonts, JSON and other resources.

Understand an HTTP request

GET /demo-data.json HTTP/1.1
Host: dsa.learnwithchampak.live
Accept: application/json

The response may resemble:

HTTP/1.1 200 OK
Content-Type: application/json

{"course":"Chrome DevTools","status":"ok"}

The examples illustrate HTTP semantics. HTTP/2 and HTTP/3 encode these messages differently on the wire.

Lab 6 — Compare success with failure (10 minutes)
  1. Open playground Lab D. Open DevTools → Network and click the Fetch/XHR filter.
  2. Click Fetch a working JSON file (200). Select demo-data.json.
  3. Read Headers for the Request URL and status, then Response for the JSON. Look at Initiator and Timing.
  4. Click Fetch a missing file (404); find this-file-does-not-exist.json.
  5. Compare the successful 200 request with the 404 error. Notice that the browser can receive a valid HTTP response even when the requested file is missing.

Expected: A successful JSON request and an intentionally missing resource appear as separate entries with different response statuses.

Request headers versus response headers

Request headers describe what the browser sends (for example, Accept or Authorization). Response headers describe what the server returns (for example, Content-Type, Cache-Control and security-related headers). Payload helps inspect submitted query strings and form or JSON bodies when applicable.

Preserve log, Disable cache and throttling

  • Preserve log: Keep records across navigation so you can investigate redirects, login flows and page transitions.
  • Disable cache: Usually prevents normal use of the browser cache while DevTools remains open. Turn it off after the experiment.
  • Throttling: Simulate slower connections or offline mode to test loading and failure behavior.
  • Request blocking: Block selected resources temporarily and watch the page react.
  • Waterfall: Study when resources began and how long their phases lasted.
Lab 7 — Investigate a slow connection (8 minutes)
  1. Open Network and enable Preserve log.
  2. Enable Disable cache and select a slower throttling preset such as Slow 3G if available.
  3. Reload the playground; watch request timings and the waterfall.
  4. Select Offline, click the working JSON button and observe the failure; restore No throttling or Online afterwards.
  5. Turn off Disable cache to avoid affecting later measurements.

Expected: A connection failure differs from an HTTP error: an HTTP 404 comes from a reached server, while offline mode may prevent any HTTP response.

HAR files: DevTools can export an HTTP Archive containing request URLs, timings, headers and possibly sensitive data such as cookies, tokens, request bodies and query parameters. Sanitise before sharing. Copy as fetch is for your own authorized debugging, not a general method of reproducing someone else's authenticated request.

Lab 8 — Save and inspect a preference (7 minutes)
  1. In playground Lab E, enter a harmless nickname (for example, Asha).
  2. Click Save in Local Storage.
  3. Open DevTools → Application → Local Storage and select the playground's origin.

Cookies have attributes worth learning: Secure requests encrypted transport; HttpOnly prevents ordinary page JavaScript reading the cookie; SameSite affects cross-site cookie sending. These attributes do not replace secure backend authentication and authorization. Never store real passwords or access tokens in plain localStorage as a teaching shortcut.

9. Device Mode: test narrow screens and responsive design

Click the phone/tablet icon in DevTools or press Ctrl + Shift + M (Mac: Cmd + Shift + M). You can choose an example device or set a responsive viewport width such as 360 CSS pixels. Rotate the viewport to inspect landscape behavior.

A CSS pixel is a layout unit; DPR (device pixel ratio) relates CSS pixels to device pixels. Responsive rules such as @media (max-width:600px) depend on viewport conditions, not the marketing name of a device.

@media (max-width: 600px) {
  .columns { grid-template-columns: 1fr; }
  .card { max-width: 100%; }
}
Lab 9 — Find horizontal overflow (7 minutes)
  1. Open playground Lab F and toggle Device Mode.
  2. Set the responsive viewport to 360 × 800 CSS pixels.
  3. Notice the wide card extending beyond the viewport.
  4. Inspect .wide-card and disable min-width:680px in Styles.
  5. Observe the difference. Test 320, 375, 768 and 1024 CSS pixel widths.

Expected: Removing a fixed minimum width helps the content fit narrow screens. Keep a record of the CSS fix for the source file.

Limitation: Device Mode is an approximation. Desktop Chrome does not become a physical Android phone. Verify important touch, keyboard, browser UI and device-specific issues on real devices.

10. Performance panel: why is my website slow?

The Performance panel records loading, scripting, style calculations, rendering and main-thread activity over time. It is useful for identifying slow JavaScript, excessive layout work and delays that affect visible page responsiveness. Use the recording controls for a page-load trace or a period of user interaction; then inspect the timeline, Main thread and Insights where available.

Three Core Web Vitals

MetricWhat it measuresCommon good threshold
LCP — Largest Contentful PaintWhen the main visible content is rendered.At most 2.5 seconds.
INP — Interaction to Next PaintResponsiveness of interactions.At most 200 milliseconds.
CLS — Cumulative Layout ShiftUnexpected visual movement.At most 0.1.

These values are user-experience targets generally assessed at the 75th percentile of real visits. A single DevTools recording is lab data, not a guarantee that real-world users meet these thresholds. CPU, browser extensions, warm caches and network quality affect results.

Lab 10 — Record a deliberate long task (10 minutes)
  1. Open playground Lab G and DevTools → Performance.
  2. Start a recording, click Simulate a ~180 ms main-thread task, then stop recording.
  3. Locate the scripting activity during the click. Zoom into the main-thread task and inspect the call tree.
  4. Compare with a recording in which you do not click the button.
  5. Write down one possible improvement: do less synchronous work on the main thread, or divide heavy work into smaller units.

Expected: The intentionally busy JavaScript handler appears as a burst of main-thread work. Exact durations differ among devices.

Performance hints: Images can delay LCP; synchronous JavaScript can slow interactions; unexpected banners or missing reserved image dimensions can contribute to CLS. Analyse the evidence before choosing an optimisation.

11. Lighthouse: a systematic website quality audit

The Lighthouse panel runs automated checks for Performance, Accessibility, Best Practices and SEO. Choose the relevant device and categories, generate the report and study individual findings. The panel can expose missing accessible names, low contrast, images without useful alternatives and avoidable performance problems.

Lab 11 — Audit the playground (10 minutes)
  1. Open DevTools → Lighthouse (use the » menu if necessary).
  2. Choose Mobile or Desktop and the categories you want to test.
  3. Run the audit. Record the scores and at least three findings.
  4. Use Elements/Styles to investigate the low-contrast examples.
  5. Explain which findings need changes in code and which are test-environment observations.

Expected: A report with actionable findings. Scores can vary between runs; do not treat a single score as a permanent property of your website.

Performance vs Lighthouse: Use the Performance panel for detailed traces and interaction debugging. Use Lighthouse for a broader automated audit. Automated checks cannot prove that a website is fully accessible or perfectly secure; manual testing remains essential.

12. Security, privacy and the Security panel

The Security panel and Console can reveal connection-security issues such as certificate problems or mixed content. Inspect HTTPS connection information and relevant certificate details. The Network panel can also show sensitive request headers or cookie information, which must not be shared carelessly.

  • Mixed content: An HTTPS page attempting to load some content via insecure HTTP may trigger blocking or warnings.
  • TLS: Protects traffic in transit when configured and authenticated correctly, but does not certify that a website is honest.
  • Cross-origin requests: Check Console and Network for CORS messages and possible preflight OPTIONS requests.
  • Permissions: Camera, microphone, clipboard and location depend on browser security rules and user permissions.
Do not confuse visibility with authorization: Being able to see HTML, JavaScript, or a request in DevTools does not give permission to access someone else's account, change server data or test unauthorized endpoints. Browser-side validation does not replace server-side security.

Most Elements edits vanish after reload. Chrome offers more persistent development workflows:

Lab 12 — Try a Local Override (advanced, 12 minutes)
  1. On a practice page, open Network and select a suitable CSS/JS/HTML resource.
  2. Use Override content where available, or open Sources → Overrides and choose a local folder.
  3. Grant Chrome access to that folder and edit the response in Sources.
  4. Reload and observe the local modified response.
  5. Disable the override and verify the original resource returns.

Expected: Your browser can use a temporary locally overridden resource. This is not a Git commit or a production deployment.

Chrome does not automatically persist ordinary DOM edits made directly in Elements through Local Overrides. To make a permanent website change, update and deploy its actual source or use a correctly configured Workspace workflow.

15. Debug a Node.js + MySQL website end to end

Consider a practical application with a frontend on a static host, a Node.js/Express API on another host, and MySQL data. Suppose clicking Load Students produces a blank table. Do not assume the database is broken.

Student browser→Frontend JavaScript→HTTPS API / Node.js→MySQL
async function loadStudents() {
  const response = await fetch("/api/students");
  if (!response.ok) {
    throw new Error("HTTP " + response.status);
  }
  const students = await response.json();
  console.table(students);
}

Diagnostic sequence: First inspect Console for JavaScript exceptions. Then open Network → Fetch/XHR and trigger the button. If no request appears, investigate the event handler. If the browser reports 404, verify the URL and route. If 401 or 403, inspect the authentication flow. If 500, inspect server-side Node.js logs. If 200 contains unexpected HTML rather than JSON, check whether a redirect or proxy returned a page. If Console reports CORS, inspect Origin, relevant response headers and any OPTIONS preflight.

Lab 13 — Write a real bug report (10 minutes)
  1. On any application you control, reproduce a harmless UI problem.
  2. Record the visible symptom, URL path and steps to reproduce.
  3. Capture a relevant Console message or Network status, hiding personal tokens/cookies.
  4. Explain whether the failure is client-side, network-layer, server-side or not yet determined.
  5. Propose one targeted code change and one verification check.

Expected: A bug report supported by evidence rather than guesses, suitable for a developer or administrator.

A systematic debugging method

  1. Reproduce: Write the exact input and action that triggers the problem.
  2. Observe: Use the right panel to gather evidence, not assumptions.
  3. Hypothesise: Form a specific explanation that can be tested.
  4. Isolate: Change one thing, minimise variables and disable interfering extensions if relevant.
  5. Fix: Modify the real source or configuration in the correct place.
  6. Verify: Repeat the original actions and check for regressions.

  1. HTML: Find the ID and tag name of the title with bad contrast.
  2. CSS: Identify the rule causing mobile overflow at 360px.
  3. JavaScript: Explain why the sum of 5 and 1 displays 51.
  4. Console: Locate the deliberate ReferenceError and its source.

18. Knowledge test with answers

1. How do you open DevTools on Windows?

Usually F12 or Ctrl + Shift + I while Chrome is focused.

2. Which panel reveals the active CSS colour?

Elements → Styles and Computed.

3. Do changes in Elements update your production server?

No. They generally affect only the current browser document and may vanish on reload or rerender.

4. Why does 5 + 1 sometimes become 51 in JavaScript?

If one or both operands are strings, + may concatenate. HTML input .value is a string.

5. Which panel diagnoses an HTTP 404?

Network; select the request and inspect URL, status, headers and initiator.

6. What is the difference between HTTP 404 and offline?

404 is an HTTP response from a server; an offline failure might prevent any response from arriving.

7. Which tab lets you inspect localStorage?

Application → Local Storage → selected origin.

8. What is a breakpoint?

A debugger control that pauses execution at a chosen statement, condition or event.

9. Does Device Mode perfectly simulate an Android phone?

No. It approximates viewport and selected conditions. Real-device testing is still needed.

10. What is a long task?

A main-thread task lasting over 50 milliseconds can interfere with timely input handling or rendering.

11. What do LCP, INP and CLS measure?

Loading of main content, interaction responsiveness and unexpected layout movement.

12. Does a good Lighthouse score prove perfect accessibility?

No. Automated tests have limits; manual keyboard, screen-reader and usability checks remain important.

13. What does Preserve log do?

It retains Network entries across navigations to help inspect redirects and flows.

14. What is Local Overrides for?

Keeping local copies of modified responses or headers for debugging across reloads, without changing the server.

15. Why must a HAR file be treated carefully?

It can contain sensitive URLs, tokens, cookies and request/response data.
