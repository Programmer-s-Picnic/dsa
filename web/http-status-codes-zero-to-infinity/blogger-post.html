1. What is an HTTP status code? Start at real zero.

When a client such as Chrome requests a webpage, file or API resource, an HTTP server ordinarily replies with a status code, headers and possibly a body. The status code is a three-digit number describing the result of that particular request. It is part of the protocol, not the filename, and the same URL can produce different codes at different times.

For example, an authorised student requesting /api/results/42 may receive 200. An unauthenticated visitor may receive 401. A different student may receive 403. A missing resource may receive 404. If backend processing fails, the server may return 500.

See a raw HTTP/1.1 response

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Cache-Control: max-age=120

<h1>Hello Students!</h1>

200 is the status number; OK is its customary reason phrase; Content-Type and Cache-Control are response headers; the HTML appears after the empty line. Modern HTTP/2 and HTTP/3 encode messages differently and do not use HTTP/1.1's textual status line, but the same status-code semantics apply.

Most important distinction: “The webpage didn't load” is not necessarily a 404 or 500. A DNS failure, TCP connection refusal, TLS failure, blocked request or offline network can prevent any usable HTTP response. Chrome may show (failed) or a browser-level error rather than a three-digit code.

2. How the browser and server exchange information

Browser / client→HTTP request→Web server / API→Status + headers + optional body→Browser

When a student presses Save Task, a JavaScript program may send a POST request. The backend validates data and checks permissions, then returns 201 if it creates a new task, 422 if a field is semantically unacceptable, 401 if authentication is missing or 500 if an unexpected failure occurs.

POST /api/tasks HTTP/1.1
Host: example.com
Content-Type: application/json

{"title":"Study HTTP"}

HTTP/1.1 201 Created
Location: /api/tasks/42
Content-Type: application/json

{"id":42,"title":"Study HTTP"}

Notice the difference between the HTTP status and a field in the JSON body. Good APIs choose meaningful statuses and use the body for additional details. A server sometimes sends a status with no body at all, particularly 204 or 304.

3. Five classes of HTTP status codes

1xxInformational — interim progress or protocol information
2xxSuccess — request successfully handled
3xxRedirection / cache revalidation
4xxClient/request error — cannot fulfil
5xxServer / intermediary error — cannot fulfil

The standards recognise valid HTTP status numbers from 100 to 599, but many numbers are unassigned. A client can recognise an unknown status by its first digit. A 4xx code doesn't prove that the user's computer is broken; a 5xx code doesn't prove the Node.js code itself is at fault, because proxies and gateways can also respond.

🎓 Champuter's memory trick

1 = Information, 2 = Success, 3 = Redirect/Reuse, 4 = Problem with fulfilling the request, 5 = Server or gateway problem. For accurate debugging, always inspect the URL, method, status, headers and body together.

5. The 1xx family — informational responses

An informational response usually arrives before the final response. A request can have zero or more 1xx responses, then one final 2xx/3xx/4xx/5xx response. You will not see these on every ordinary webpage.

StatusMeaning
100 ContinueAn interim response signalling that request body transmission may proceed.
101 Switching ProtocolsServer agrees to upgrade the protocol when the client requested a supported switch.
103 Early HintsAn interim response that can help the browser begin loading likely resources early.

100 Continue

The client may send Expect: 100-continue before a large request body. The server can reply 100 to indicate continuation. This is useful when avoiding the cost of uploading a large body that the server would immediately reject.

101 Switching Protocols

Can be used in an HTTP/1.1 protocol upgrade, historically associated with WebSocket handshakes. HTTP/2 and HTTP/3 introduce different mechanisms.

103 Early Hints

Can supply preliminary link hints before the final response, potentially enabling earlier preload/preconnect work. Intermediaries and browser versions affect whether these details are visible in DevTools.

200, 201, 202 and 204 are not interchangeable

200 OK: the server successfully completed a request. 201 Created: a new resource exists; a Location response header may identify it. 202 Accepted: work was accepted, but might still fail later, so an asynchronous job-status endpoint may be useful. 204 No Content: no response body should be parsed as JSON.

GET    /api/tasks/42 → 200 OK

POST   /api/jobs     → 202 Accepted

206 Partial Content usually involves a request like Range: bytes=0-9 and a response Content-Range: bytes 0-9/28. This is used for media playback and partial downloads.

7. The 3xx family — redirecting and reusing cached resources

StatusMeaningKey detail

302 FoundA temporary redirect.Browsers may change POST to GET historically.

Understand 301, 302, 303, 307 and 308

When a resource moves, a server can return a redirect with a Location header. Browsers usually follow it automatically. 301 and 308 are permanent; 302 and 307 are temporary. 307 and 308 preserve the original HTTP method and body; 301/302 may change POST to GET for compatibility. A 303 commonly directs the client to fetch a result using GET after a successful POST.

POST /submit-form
HTTP/1.1 303 See Other
Location: /thank-you

GET /thank-you
HTTP/1.1 200 OK

304 is a special case: Not Modified

A 304 is a revalidation response, not an ordinary redirection to another URL. The browser might send If-None-Match containing an ETag from a previous response. If the resource remains unchanged, the server returns 304 and the browser can reuse the cached representation. A 304 has no response body.

GET /lesson.css HTTP/1.1
If-None-Match: "version-7"

HTTP/1.1 304 Not Modified
ETag: "version-7"

8. The 4xx family — client and request errors

4xx means the server cannot or will not fulfil the request. This is broader than a typo in the browser. The resource may be private, the authentication may be missing, the JSON may violate application rules, or the route may be unavailable.

401 vs 403

401: the request lacks valid authentication. Despite its name “Unauthorized”, it usually means authenticate first. RFC 9110 requires an applicable WWW-Authenticate challenge in a 401 response. 403: the server understands but refuses the request, often due to a permissions rule. A resource can sometimes be reported as 404 to avoid revealing its existence.

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="Students"
Content-Type: application/json

{"error":"Please sign in"}

405 Method Not Allowed

A route supporting GET may reject POST with 405. The server must include an Allow response header identifying its supported methods. This is different from a 501 response, where the server does not implement the method at all.

POST /api/only-get

HTTP/1.1 405 Method Not Allowed
Allow: GET, HEAD, OPTIONS

429 Too Many Requests and Retry-After

A client may exceed a rate limit and receive 429, potentially with Retry-After: 10. It should wait and apply reasonable backoff. Do not immediately retry continuously, especially not a POST that could create duplicate records without idempotency controls.

9. The 5xx family — servers and gateways fail

A 5xx response means a server or intermediary could not fulfil an apparently valid request. The error may arise in your application, web server, reverse proxy, load balancer or another backend service. The HTTP code helps direct your investigation, but cannot by itself reveal the precise broken component.

CodeMeaning and initial diagnosis
500 Internal Server ErrorGeneric internal failure; inspect app logs, error handlers and request IDs.
501 Not ImplementedServer does not support the requested HTTP method/functionality.
502 Bad GatewayGateway/proxy received an invalid response from an upstream server.
503 Service UnavailableTemporary maintenance or overload; may include Retry-After.
504 Gateway TimeoutGateway/proxy waited too long for an upstream response.
505 HTTP Version Not SupportedServer does not support the request's HTTP version.
506 Variant Also NegotiatesServer content-negotiation configuration error.
507 Insufficient StorageWebDAV operation could not be performed due to insufficient storage.
508 Loop DetectedWebDAV operation detected an infinite loop.
511 Network Authentication RequiredClient needs network-access authentication (such as captive portal).

500 vs 502 vs 503 vs 504

500 Internal Server Error is the general failure response. It may originate in backend code, unexpected data or integration errors. 502 Bad Gateway means an intermediary received an invalid upstream response. 503 Service Unavailable signals temporary unavailability, often overload or maintenance, and may include a Retry-After header. 504 Gateway Timeout means an intermediary did not receive a timely upstream response.

Chrome→Reverse proxy→Node.js API↔MySQL

When investigating 502/504, inspect reverse-proxy logs, service health, network routing and upstream timings. For 500, inspect backend errors and relevant request IDs. For 503, inspect capacity, maintenance, deployment state and retry guidance.

Local-lab accuracy: The provided Node.js server deliberately returns the numeric 500, 502, 503 and 504 codes. Those HTTP responses are real; the simulated explanations do not mean that a database actually failed or that an upstream server really timed out. This protects the lesson from causing unnecessary infrastructure failures.

12. JavaScript fetch(): HTTP errors are not always thrown exceptions

One of the most important practical facts: fetch() does not normally reject just because a server returns HTTP 404 or 500. It resolves with a Response object; the script must examine response.status or response.ok. A network failure, invalid URL or blocked request can reject the Promise instead.

async function loadStudents() {
  try {
    const response = await fetch("/api/students");

    console.log(response.status);
    console.log(response.ok); // true for 200–299

    if (!response.ok) {
      throw new Error("HTTP " + response.status);
    }

    const students = await response.json();
    console.table(students);
  } catch (error) {
    console.error("Request failed:", error.message);
  }
}

204: do not attempt to parse a body that is absent

const response = await fetch("/api/task/42", {
  method: "DELETE"
});

if (response.status === 204) {
  console.log("Deleted successfully.");
} else if (response.ok) {
  const result = await response.json();
  console.log(result);
} else {
  console.error("HTTP error:", response.status);
}

Why a redirect can appear as 200 in your JavaScript

Fetch usually follows redirects automatically. If the original response is 303 and the final destination returns 200, the resolved Response may show 200, while DevTools Network reveals the preceding 303. You can check response.redirected and response.url, but do not rely on a post-hoc check to protect against unsafe redirect targets.

13. Create real status responses with Node.js and Express

When designing an API, choose a status that matches the operation's semantics. This makes life easier for frontend developers, monitoring systems, retries and API clients.

GET    /api/tasks       → 200 OK
POST   /api/tasks       → 201 Created
POST   /api/reports/run → 202 Accepted
DELETE /api/tasks/42    → 204 No Content
GET    /api/tasks/999   → 404 Not Found
POST   /api/tasks       → 422 Unprocessable Content
GET    /api/private     → 401 Unauthorized
GET    /api/admin       → 403 Forbidden
GET    /api/limited     → 429 Too Many Requests

A small working Express illustration

const express = require("express");
const app = express();
app.use(express.json());

const tasks = [{ id: 1, title: "Study HTTP" }];

app.get("/api/tasks", (req, res) => {
  res.status(200).json(tasks);
});

app.post("/api/tasks", (req, res) => {
  const title = req.body && req.body.title;
  if (typeof title !== "string" || !title.trim()) {
    return res.status(422).json({
      error: "A nonempty title is required"
    });
  }

  const task = { id: tasks.length + 1, title: title.trim() };
  tasks.push(task);
  res.location("/api/tasks/" + task.id)
     .status(201).json(task);
});

app.get("/api/tasks/:id", (req, res) => {
  const task = tasks.find(t => t.id === Number(req.params.id));
  if (!task) return res.status(404).json({error:"Not found"});
  return res.json(task);
});

app.listen(3000, "127.0.0.1");

This minimal example uses in-memory data solely for teaching. Production APIs need authenticated requests, per-record authorisation, persistent storage, input validation, proper error handling and safe deployment.

16. Advanced issues: cache, standards, security and vendor codes

404 is not necessarily uncached

HTTP caching rules allow some responses, including 404, to be cached heuristically unless headers or other rules prevent it. If a page has recently been created but the browser still reports 404, check cache/CDN behaviour as well as the route.

304 and 204 must not carry ordinary message bodies

Do not automatically call response.json() after these statuses. The browser may reuse previously cached content after a 304, even though that new 304 message has no body.

Conditional writes and 412

Suppose two teachers edit the same lesson. The first fetches ETag "v1". The second changes the record. The first teacher sends an update with If-Match: "v1". The server can return 412 when that condition is no longer true, preventing an accidental overwrite. A 428 can require a conditional request.

Do not use 200 for every application error

An API that always returns 200 and hides {"success":false} inside a body makes monitoring, error handling and caching misleading. Match status and body to the actual API contract.

418, 499 and 52x

418 is famous for the “I'm a teapot” joke, but the current IANA and RFC 9110 registry marks it (Unused). Nginx's 499 and certain CDN 52x responses are vendor-specific; investigate their vendor documentation rather than presenting them as universally standard codes.

Privacy when exporting DevTools requests

Chrome's Copy as cURL and HAR exports can reveal session cookies, authorization headers, query values or submitted data. Sanitise them before sharing, and do not paste unknown scripts into the DevTools Console.

17. Self-assessment: 20 questions with answers

1. Does HTTP 404 mean the browser failed to contact the server?

No. A normal 404 is a response from a server or intermediary.

2. What does 201 convey?

Successful creation of a resource, often with Location.

3. Does 202 guarantee the job has finished?

No. It only says the job/request was accepted.

4. May 204 contain JSON?

No. It has no response body.

5. What is 206 for?

Returning partial byte ranges of content.

6. Which redirect is permanent: 301 or 302?

301 is permanent; 302 is temporary.

7. Which redirects preserve the original method and body?

307 and 308.

8. Why might fetch show 200 after a 303?

Fetch followed the redirect to a final 200 response.

9. Is 304 a redirect to another URL?

No. It is cache revalidation.

10. What does 401 mean?

Valid authentication is absent; a WWW-Authenticate challenge is required.

11. How does 403 differ from 401?

403 is refusal; 401 concerns missing/invalid authentication.

12. What does 404 mean?

Requested resource was not found or was intentionally concealed.

13. What is 405?

Method Not Allowed. The response must include Allow.

14. What differs between 409 and 412?

Conflict with resource state vs a failed conditional precondition.

15. Which code describes unsupported Content-Type?

415 Unsupported Media Type.

16. What is 422?

Unprocessable Content — understood syntax but unacceptable semantics.

17. What does 429 signify?

Too many requests; client should back off and follow Retry-After if supplied.

18. How are 502 and 504 different?

502 is invalid upstream response; 504 is upstream timeout.

19. Does fetch() reject solely because the HTTP status is 500?

Normally no. It resolves with a Response; response.ok is false.

20. Is 418 an ordinary standard production status?

It is marked (Unused) in the current registry.
