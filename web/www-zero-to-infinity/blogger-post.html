1. What does WWW mean? Is WWW the Internet?

WWW means World Wide Web, often called simply the Web. It is a system of linked documents and other resources identified by web addresses and accessed using technologies such as HTTP and HTTPS. The Web runs over the Internet, but the two are not the same.

The Internet is a worldwide collection of interconnected networks that transport data. The Web is one important application that uses this network infrastructure. Email, SSH, internet calling and online gaming also use the Internet, but they are not necessarily part of the World Wide Web.

Internet = infrastructure

Routers, links, providers, networks, IP addressing and packet delivery. Think of the road system.

Web = information/service system

Webpages, websites, URLs, hyperlinks, browsers and HTTP(S). Think of the shops and buildings reached using the roads.

Here is a subtle but important detail: www at the beginning of www.example.com is often just a subdomain name. Many websites work perfectly at example.com without the www prefix. The three letters are neither a required part of HTTPS nor a magical command.

https://www.example.com/
        └─ subdomain: www

https://example.com/
        └─ domain without www

Both may point to the same website,
or the site may redirect one to the other.

2. How did the Web begin?

Tim Berners-Lee proposed a hypertext information-sharing system at CERN in 1989. In 1990, he developed core pieces of the first Web system, including a browser/editor, a web server and webpages; in 1991, he publicly announced the project. The Web's central insight was to link resources so that people could move between documents simply by clicking hyperlinks.

Three central Web building blocks emerged: URL to identify a resource, HTTP to request and transfer Web content, and HTML to describe hypertext documents. CSS and JavaScript later made pages richer, styled and interactive. The Web is now used for documents, multimedia, web applications and APIs.

URL: Where?+HTTP: How to communicate?+HTML: What is the document?

4. Client and server: the Web's most useful mental model

A client is software that asks for a service; a server is software that provides one. Usually the browser acts as the client. Web server software listens for requests and returns responses. A single physical machine may run multiple servers; conversely, one website may use many machines.

Browser / client→ Request →Server→ Response →Browser / client

Some resources are static: an HTML or image file can be returned without executing business logic. Other resources are dynamic: a backend program may check permissions, query a database, compute results and build a response. Static and dynamic content often coexist.

Web server versus application server versus database

A reverse proxy or web server can handle incoming HTTPS traffic. An application server runs your program (such as a Node.js Express app). A database stores organised data (such as MySQL or PostgreSQL). The roles can run on one computer for a small project or on separate systems for a larger service.

Browser→HTTPS / reverse proxy→Node.js application↔MySQL database

A frontend stored on GitHub Pages and a backend hosted elsewhere can be part of one web app. Their distinct origins introduce cross-origin considerations later in this lesson.

5. How a browser reaches a distant server: IP, DNS, packets and ports

When you request a website, the browser needs a way to locate a reachable network endpoint. A DNS resolver can look up a hostname and return address records such as IPv4 (A) or IPv6 (AAAA). Routers forward network packets toward the destination. The client then establishes the applicable transport connection.

IP address and DNS

Hostname:  www.example.com
DNS:       resolves name to an address
Example:   203.0.113.10  (documentation-only IP)

Browser → network → destination endpoint

DNS lookup may be skipped if a usable cached answer exists. Real website infrastructure can use many addresses, load balancers, caches and CDNs, so a hostname does not necessarily correspond to one permanent server.

What is a port number?

An IP address helps reach a network endpoint; a port distinguishes a transport service or connection endpoint. Think building address versus numbered office. The numeric range for TCP and UDP ports is 0–65535 (port 0 has special/reserved meaning for ordinary service use). TCP 443 and UDP 443 are different endpoints.

Example portCommon use
80/TCPHTTP
443/TCPHTTPS using HTTP/1.1 or HTTP/2
443/UDPHTTP/3 over QUIC
53/UDP or TCPConventional DNS
22/TCPSSH
3000/TCPFrequently a local Node.js development server, not a required HTTP port
3306/TCPCommon default MySQL port

http://localhost:3000 requests an HTTP service on port 3000 of your own computer; /students after that identifies an application route. A port is not a route, and a firewall allowing a port does not guarantee a program is listening there.

TCP versus QUIC

HTTP/1.1 and HTTP/2 commonly use TCP; secure use also involves TLS. HTTP/3 uses QUIC, which runs over UDP and includes secure, reliable stream transport. Therefore it is inaccurate to claim that every HTTP connection always uses TCP.

6. Understand every part of a web address (URL)

A URL (Uniform Resource Locator) identifies how to locate a resource. Study this illustrative address:

https://www.example.com:443/courses/web?level=0&lang=en#cookies
└https┘ └──hostname─────┘ └┘ └──path────┘ └query string┘ └fragment┘

https      = scheme (secure HTTP)
www        = subdomain / host label
example.com= domain
:443       = explicit port, normally implicit for HTTPS
/courses/web = path
?level=0&lang=en = query parameters
#cookies   = fragment handled on the client side

URL fragments are normally not sent as part of an HTTP request target to the server. Query parameters usually are. Avoid putting passwords, access tokens or other sensitive values into URLs because they can be recorded in logs, browsing history or shared links.

Two URLs differing by scheme (http versus https), hostname or port usually represent different origins. Paths and query strings do not change the origin. We will use this important distinction for cookies, storage and CORS.

7. HTTP: the conversation between browser and server

HTTP means Hypertext Transfer Protocol. It defines request/response semantics for webpages, images, JSON APIs and other resources. Usually a client sends a request and a server replies with a status, headers and optionally a body. Modern web pages often generate many requests, not just one.

HTTP/1.1 request example

GET /courses/web HTTP/1.1
Host: example.com
Accept: text/html
User-Agent: ExampleBrowser/1.0

HTTP/1.1 response example

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Cache-Control: max-age=120

<!doctype html>
<html><body>
  <h1>Welcome!</h1>
</body></html>

HTTP/2 and HTTP/3 have different underlying wire formats, but these request and response ideas remain. A header is metadata; a body carries content. The Content-Type header tells the client how to interpret the body.

8. HTTPS, encryption, TLS and certificates

HTTPS is HTTP protected by TLS (Transport Layer Security). TLS helps ensure that data is encrypted in transit, resistant to undetected alteration, and exchanged with a server whose identity is authenticated through correctly validated certificates.

Browser→TLS handshake and keys→Encrypted HTTP→Server

A certificate binds an identity (such as a hostname) to a public key through a certificate trust system. The browser checks relevant details such as domain name, validity and trust chain. Modern HTTPS uses TLS (not the obsolete SSL protocol), even though people sometimes say “SSL certificate.”

HTTP

Normally port 80, without built-in connection encryption. Unsafe for transmitting passwords over untrusted networks.

HTTPS

Normally port 443; HTTP messages are protected by TLS or QUIC's TLS-based security, depending on HTTP version.

HTTPS protects the transport but does not guarantee that a website is honest, that its content is harmless, or that the server stores data securely. A phishing site may have a valid TLS certificate.

Remember: Do not use live passwords or secrets in browser practice pages. Even on HTTPS sites, browser scripts or compromised servers can introduce separate risks.

9. HTML: structure and meaning of a web document

HTML means HyperText Markup Language. It is the markup language of Web documents: elements express headings, paragraphs, links, forms, images, tables and meaningful document structure. HTML is not the same as a general-purpose programming language.

<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport"
        content="width=device-width, initial-scale=1">
  <title>My First Webpage</title>
</head>
<body>
  <header>
    <h1>Welcome to my website</h1>
  </header>
  <main>
    <p>This is a paragraph.</p>
    <a href="https://example.com">Visit example</a>
    <button type="button">Click me</button>
  </main>
</body>
</html>

Tags, elements and attributes

<p> is an opening tag, </p> a closing tag, and the complete paragraph is an element. Attributes such as href, id, class, alt and lang describe properties or relationships.

Semantic HTML and accessibility

Use <header>, <nav>, <main>, <article>, <section> and <footer> when they match the document's meaning. Choose headings in logical order. Use a real <button> for actions and an <a> for navigation. Give informative images appropriate alternative text.

10. CSS: making HTML look beautiful

CSS means Cascading Style Sheets. CSS controls colours, fonts, spacing, borders, position, alignment, responsive layouts and much of a page's visual presentation. HTML says what an element is; CSS says how it looks and is laid out.

<style>
  body {
    background: #f0f8ff;
    color: #163e5c;
    font-family: Arial, sans-serif;
  }
  .card {
    padding: 20px;
    border: 1px solid #b4d8ed;
    border-radius: 12px;
    background: white;
  }
  .card button:hover {
    background: #155e96;
    color: white;
  }
</style>

<div class="card">
  <h2>Hello!</h2>
  <button type="button">Start</button>
</div>

The selector body selects the body element, .card selects a class, #menu selects an ID, and :hover matches a state. The cascade determines which declarations win when several rules apply, based on origins, importance, layers, specificity and order.

The box model

Margin→Border→Padding→Content

Every common layout box has a content area plus padding, border and margin. With box-sizing:border-box, the declared width includes padding and border, which often makes responsive layouts easier to reason about.

Flexbox, Grid and mobile responsiveness

/* Flexbox: align items in one dimension */
.menu { display: flex; gap: 12px; }

/* Grid: build a responsive card layout */
.products {
  display: grid;
  grid-template-columns:
    repeat(auto-fit, minmax(220px, 1fr));
  gap: 16px;
}

/* Change layout on narrow screens */
@media (max-width: 600px) {
  .menu { flex-direction: column; }
}

11. JavaScript: behaviour and interactivity

JavaScript is a programming language used by browsers for interactions and dynamic document updates. It also runs outside browsers, including on servers using Node.js. It can react to clicks, read forms, update content, fetch data and coordinate more complex web applications.

Understand the DOM

When the browser parses HTML, it creates a Document Object Model (DOM), representing the current document as connected nodes. JavaScript can read and change these nodes; CSS determines their appearance.

<p id="greeting">Hello!</p>
<button type="button" id="helloButton">
  Say hello
</button>

<script>
  const button = document.getElementById("helloButton");
  const greeting = document.getElementById("greeting");

  button.addEventListener("click", () => {
    greeting.textContent = "Hello from JavaScript!";
  });
</script>

The event listener waits for a click. textContent updates the paragraph without reloading the page. It is generally safer than putting untrusted user input into innerHTML, which can create cross-site scripting vulnerabilities when misused.

Client-side versus server-side JavaScript

Browser JavaScript

Handles UI, forms, DOM events, local storage, calling APIs and rendering. Its code can often be inspected by the user.

Server-side Node.js

Receives requests, applies trusted business rules, verifies permissions, works with databases and sends responses.

A critical principle: Never rely on browser-side validation as your only security check. A user can change browser scripts or send requests without using your intended interface. Server logic must validate and authorise operations.

12. How HTML, CSS and JavaScript become pixels

After a successful navigation, the browser may receive HTML, parse it into the DOM, discover additional CSS/JavaScript/image resources, compute styles, determine layout and paint pixels. JavaScript can modify elements and trigger further style or layout work. CSS and script loading rules affect when portions of the page become usable.

HTML bytes→DOM+CSS rules→Style + Layout→Paint + Compose

JavaScript execution, font loading, images, animations, caching and different rendering engines influence the details. A page can become partially visible before all resources finish loading. A single website visit can involve dozens or hundreds of separate network requests.

Why pages sometimes jump or freeze

Large images without reserved dimensions can cause layout movement. Long-running synchronous JavaScript can delay user interaction and painting. Too many blocking resources can delay initial rendering. Chrome DevTools has Elements, Network, Performance and Lighthouse tools for investigating these problems.

13. Forms: how the browser collects information

HTML forms provide inputs, labels, select boxes, checkboxes and submission controls. A form's action identifies where information is submitted; method controls the HTTP request method. A backend must validate submissions regardless of browser validation.

<form action="/search" method="get">
  <label for="q">Search</label>
  <input id="q" name="q" required>
  <button type="submit">Search</button>
</form>

A GET form normally puts submitted values in the query string (such as /search?q=html). A POST form normally sends values in the request body. POST is not encryption: sensitive forms need HTTPS and server-side protection. Avoid placing passwords in URLs.

GET versus POST: deeper meaning

GET is intended for retrieval and is defined to be safe in HTTP semantics. POST submits content for processing and may change server state. If a GET endpoint deletes data, that is an unsafe application design even though a programmer could technically implement it.

14. APIs and JSON: when webpages talk to programs

API means Application Programming Interface. Web APIs commonly expose HTTP endpoints from which a browser or another program can request or update data. JSON is a lightweight text format representing objects, arrays, strings, numbers, booleans and null values.

{
  "student": "Asha",
  "subject": "Web Development",
  "marks": 92,
  "passed": true
}

JavaScript fetch() example

async function loadLessonData() {
  const response = await fetch(
    "https://dsa.learnwithchampak.live/web/www-zero-to-infinity/sample-api.json"
  );

  if (!response.ok) {
    throw new Error("HTTP " + response.status);
  }

  const data = await response.json();
  console.log(data);
}

loadLessonData().catch(console.error);

Note that fetch() does not automatically reject merely because a server returned HTTP 404 or 500. Check response.ok or response.status. A network failure can reject the Promise itself. Cross-origin reading also depends on the browser's CORS rules.

15. Backend programs, databases and multi-tier applications

A dynamic application might have several stages: a browser displays a form; JavaScript sends an API request; a Node.js application checks input and permissions; a database stores or returns records; the application sends JSON; JavaScript updates the page.

UI / browser→HTTP API→Business logic→Database

Database systems such as MySQL and PostgreSQL use tables and SQL queries; other databases have different models. Never send raw database credentials to the browser. Browser scripts are not a protected place for secrets.

Example API journey: task manager

Browser sends:
POST /api/tasks
Content-Type: application/json

{"title":"Study HTML"}

Backend:
1. Check session and permissions
2. Validate title
3. Insert into database
4. Return new task ID

Response:
HTTP/1.1 201 Created
Content-Type: application/json

{"id":12,"title":"Study HTML"}

Real applications also need robust error handling, rate limiting where appropriate, safe database queries, permission checks and backups.

16. Why HTTP is called stateless

HTTP is stateless in the sense that each request does not automatically include the history of all previous requests in its protocol semantics. A browser can request /home and later /profile; without additional state management, the server does not automatically know that both requests belong to one logged-in user.

Request 1: /home→Response 1·Request 2: /profile→Response 2

However, web applications can maintain user continuity. They use cookies, server-side sessions, tokens, database records and other state-management mechanisms. Stateless HTTP does not imply stateless applications.

17. Cookies: small pieces of browser-managed state

A cookie is a small name/value item associated with a website. A server can set a cookie using the Set-Cookie response header. Subject to browser policies and the cookie's attributes, the browser later includes matching cookies in HTTP requests using the Cookie request header.

The simplest cookie example

Server response:
HTTP/1.1 200 OK
Set-Cookie: theme=blue; Path=/; SameSite=Lax

Later browser request:
GET /lessons HTTP/1.1
Host: example.com
Cookie: theme=blue

The browser manages when the cookie is attached. The server can read the Cookie header. JavaScript can access cookies without HttpOnly through document.cookie, but HttpOnly session cookies are intentionally hidden from page JavaScript.

Why websites use cookies

  • Sessions: hold an opaque login-session identifier so later requests can be associated with a server-side session.
  • Preferences: remember language, layout or theme settings.
  • Shopping carts: identify a visitor or related cart record.
  • Analytics and advertising: some cookies help recognize activity across visits, subject to laws and browser privacy controls.

Cookie attributes explained individually

AttributeMeaningWhy it matters

Session cookies versus persistent cookies

A cookie without an explicit Expires or Max-Age is commonly called a session cookie. Its lifetime is controlled by browser session behaviour; session restoration may preserve it. A cookie with a specified lifetime is usually a persistent cookie. A browser cookie called a “session cookie” must not be confused with the server-side session record it may identify.

Example secure authentication cookie header

Set-Cookie: __Host-sid=OPAQUE_RANDOM_SESSION_ID;
            Path=/; Max-Age=1800;
            Secure; HttpOnly; SameSite=Lax

The special __Host- prefix has browser-enforced restrictions in supporting browsers (including no Domain attribute and a Path=/ requirement). Never copy this literal value as a production credential: a legitimate session identifier must be securely random and generated by a trusted session manager.

Important: Do not store plaintext passwords or unprotected personal data inside cookies. Cookies can be modified by the user unless protected by appropriate server-side validation or cryptographic mechanisms. Cookie consent and privacy obligations depend on jurisdiction and use.

18. Server-side login sessions — not the same as sessionStorage

A server-side session is a server-maintained association between an identifier and application state such as a logged-in user, expiry and selected session data. A common design places an opaque session ID in a browser cookie while keeping sensitive account/session information on the server or in a session store.

Login story, one request at a time

  1. The visitor submits credentials over HTTPS.
  2. The server checks them using secure password verification or a trusted identity provider.
  3. The server creates a new unpredictable session identifier, recording its association with the authenticated user.
  4. The server sends an HttpOnly, Secure, appropriately scoped cookie containing the session ID.
  5. For later requests, the browser automatically attaches this cookie when matching rules allow.
  6. The server looks up/validates the session ID and determines who the visitor is and whether access is allowed.
  7. At logout, the server invalidates the session and clears or expires the cookie.
Login form→Server verifies→Session store→Cookie with session ID→Later protected request

Why not place the username and password in a cookie?

Every request would risk unnecessarily transmitting sensitive credentials; browser storage can be attacked or exposed. A random session ID is not a password and can be revoked centrally. It is still a highly sensitive credential in practice: whoever holds a valid session ID may be able to act as that user, so it needs protection.

Session fixation, expiration and logout

Regenerate the session ID when privilege level changes (especially after login), apply idle and absolute expiration policies, and invalidate sessions on logout. A session may also be invalidated when a user changes a password or an administrator revokes access. A user merely closing a browser tab does not guarantee that a server session has ended.

Sessions versus cookies in one line

Cookie: browser-managed data (often just the opaque session ID). Server session: application state associated with that ID and verified by the backend.

19. localStorage, sessionStorage, IndexedDB and in-memory state

The Web Storage API provides localStorage and sessionStorage. Both store string key/value pairs in the browser and are accessed by JavaScript. They do not automatically travel in ordinary HTTP request headers. Storage access is limited by browser origins and policies.

localStorage example

// Set a harmless preference
localStorage.setItem("theme", "lightblue");

// Read it
const theme = localStorage.getItem("theme");
console.log(theme);

// Remove just one key
localStorage.removeItem("theme");

localStorage normally persists across page reloads, tabs and browser restarts for the same origin, until removed by the application, user, browser policy, quota management or private-browsing behaviour. Persistence is not guaranteed forever.

sessionStorage example

sessionStorage.setItem("draftTitle", "My WWW lesson");
console.log(sessionStorage.getItem("draftTitle"));
sessionStorage.removeItem("draftTitle");

sessionStorage is partitioned by origin and page session (usually a tab). It normally survives reloads in that tab but is cleared when the page session ends. A new tab created with an opener or duplicated tab may begin with a copied sessionStorage state; thereafter the stores are independent.

JSON requires serialization

const preferences = {
  language: "English",
  fontSize: 18
};

// Store as a string
localStorage.setItem(
  "preferences",
  JSON.stringify(preferences)
);

// Read back as an object
const saved = JSON.parse(
  localStorage.getItem("preferences") || "{}"
);

console.log(saved.language);

Since storage values are strings, storing an object directly without JSON serialization does not give you a recoverable nested JavaScript object.

What about IndexedDB?

IndexedDB is a browser database for more substantial structured client-side data and transactional operations. It is useful for offline applications, larger data sets and more complex indexing. Cache Storage separately holds Request/Response pairs, often used by service workers.

What about ordinary JavaScript variables?

A variable such as let cart=[] exists in an execution environment while the page's scripts run. Reloading normally recreates that state unless the app restores it. Browser storage and server records are strategies for persistence beyond a single running script.

Security rule: Do not store session IDs, access tokens or confidential personal information in localStorage as a casual shortcut. If malicious JavaScript executes on your origin, it can generally read these values. A secure server-issued HttpOnly cookie is often preferable for traditional website sessions, with other protections still required.

Champuter's memory trick:

Cookie travels with matching HTTP requests; localStorage stays in browser storage; sessionStorage stays with a page session; server session is the backend's record of an authenticated or otherwise stateful interaction. A browser cookie often ties the first and fourth together.

21. Authentication, authorization and accounts

Authentication asks: Who are you? Authorization asks: What may you access or change? A valid login alone does not permit a student to read another student's private marks.

Registration, login and logout

Registration creates an account record. Login checks identity and establishes an authenticated session (or other trusted credential). Logout invalidates that authenticated session. A password should never be stored directly in plaintext; production applications use a vetted, salted, password-hashing function such as Argon2id or another suitable industry-recognised method.

Roles and protected routes

// Illustrative server-side checks
if (!req.session.userId) {
  return res.status(401).json({error:"Login required"});
}

if (req.session.role !== "admin") {
  return res.status(403).json({error:"Forbidden"});
}

Even if a browser hides an admin button, a malicious client can attempt the URL directly. The server must check permissions for every protected action.

OAuth and “Sign in with Google”

Federated sign-in delegates identity verification through an identity provider. Proper OAuth/OpenID Connect implementations validate tokens and protocol state, but your application must still decide how user accounts and permissions work. Never treat a URL parameter like ?username=admin as proof of identity.

22. Same-origin policy, CORS, CSRF and XSS

A browser origin is the tuple scheme + hostname + port. Example:

https://example.com     origin A
http://example.com      origin B (different scheme)
https://example.com:8443 origin C (different port)
https://api.example.com origin D (different host)

Same-origin policy and CORS

Browsers restrict what scripts on one origin can read from another origin unless allowed by relevant policies. CORS (Cross-Origin Resource Sharing) is an HTTP-header mechanism that can permit authorised cross-origin reads by browser JavaScript. It is not a substitute for authentication or an API firewall.

Access-Control-Allow-Origin: https://example.com
Access-Control-Allow-Methods: GET, POST
Access-Control-Allow-Headers: Content-Type

Some non-simple cross-origin requests cause a browser OPTIONS preflight. When credentialed CORS requests are used, the server must apply additional restrictions; wildcard origins cannot be combined with credentialed responses. Cookies also obey their own SameSite and credential policy, independently of CORS.

CSRF: Cross-Site Request Forgery

CSRF occurs when an attacker tricks an authenticated browser into issuing an unwanted request to another site. Because cookies can be attached automatically, protected state-changing routes need CSRF defences, potentially including anti-CSRF tokens, SameSite cookies, Origin/Referer checks and fetch metadata checks. Relying on a POST method alone is not enough.

XSS: Cross-Site Scripting

XSS occurs when malicious input is interpreted as executable content in a trusted webpage. It can access non-HttpOnly data, modify UI or make requests in a user's session. Mitigations include contextual output encoding, safe DOM APIs such as textContent, input handling suited to context, a strong Content Security Policy (CSP) and careful review of third-party scripts.

Other essential protections

  • SQL injection: use parameterised SQL queries, never concatenate untrusted input into SQL commands.
  • Clickjacking: use suitable framing restrictions such as frame-ancestors CSP.
  • Mixed content: avoid insecure HTTP resources on an HTTPS page.
  • Rate limiting: constrain abuse of sensitive endpoints.
  • Least privilege: give each account and process only the permissions it needs.
Champuter's security principle: Nothing in the browser is a trustworthy secret or permission check. Protect it for user experience, but enforce real security on the server.

23. Caching, CDNs, service workers and offline webpages

Caching avoids fetching the same content unnecessarily. A browser cache, reverse proxy or CDN may store suitable responses. HTTP caching directives such as Cache-Control, ETag and Last-Modified help determine reuse and validation.

Cache-Control: public, max-age=3600
ETag: "lesson-version-7"

A CDN (Content Delivery Network) distributes or caches content at geographically spread locations, potentially reducing latency. A service worker is a browser-controlled script that can intercept selected requests, support offline experiences and manage Cache Storage. A PWA (Progressive Web App) combines Web technologies with capabilities such as installability and potentially offline functionality, subject to platform support.

Be cautious about caching personalised responses. A shared cache should not accidentally serve one user's private content to another. Use appropriate cache headers and authentication-aware design.

25. What is cloud hosting? Where does a website live?

Websites are hosted on real computers and storage devices. Cloud computing describes a service model in which infrastructure, storage, databases or applications are made available on demand and managed through provider services. “Cloud” is not an invisible physical location.

Shared hosting

Multiple websites use provider-managed servers; limited infrastructure control.

Virtual Private Server

An isolated virtual server environment with more configuration responsibility.

Cloud infrastructure

Provisionable compute, storage, networks and managed services, often with elasticity.

Static hosting

Publishes static site assets, frequently backed by object storage/CDNs.

The domain-to-server journey

Buy/configure domain→Publish DNS records→Host page/backend→Configure HTTPS→Test and monitor

Hosting does not eliminate responsibility for access controls, secrets, backups, software updates or billing. Some public clouds are self-service and elastic; ordinary shared hosting may provide only a subset of cloud characteristics. A website does not have to use any particular cloud provider to belong to the World Wide Web.

27. Practical Node.js project: HTTP, HTML, API, cookie and a real server session

Here is a small but genuine local example using Node.js, Express and express-session. It shows a GET route, a POST request, server session state, protected content and logout. For simplicity it uses a demo visitor identity rather than passwords. It is a teaching demonstration, not a ready-to-deploy public authentication system.

Step 1: create a project

mkdir www-practice
cd www-practice
npm init -y
npm install express express-session

Step 2: create server.js

"use strict";

const express = require("express");
const session = require("express-session");
const crypto = require("node:crypto");

const app = express();
const PORT = Number(process.env.PORT) || 3000;

// Set a secret through an environment variable.
// Local ephemeral fallback is only for this demo:
const secret = process.env.SESSION_SECRET ||
  crypto.randomBytes(32).toString("hex");

app.use(express.urlencoded({ extended: false }));
app.use(express.json());

app.use(session({
  name: "www_demo_sid",
  secret,
  resave: false,
  saveUninitialized: false,
  cookie: {
    httpOnly: true,
    sameSite: "lax",
    secure: false, // local HTTP only; true for HTTPS production
    maxAge: 30 * 60 * 1000
  }
}));

function escapeHtml(value) {
  return String(value)
    .replaceAll("&", "&")
    .replaceAll("<", "<")
    .replaceAll(">", ">")
    .replaceAll('"', """)
    .replaceAll("'", "'");
}

app.get("/", (req, res) => {
  const name = req.session.displayName;
  res.type("html").send(`
    <h1>WWW Demonstration</h1>
    <p>${name ?
      "Hello, " + escapeHtml(name) :
      "You are a guest."}</p>

    <form action="/login" method="post">
      <label>Demo name:
        <input name="displayName" maxlength="40"
               required>
      </label>
      <button>Enter demonstration</button>
    </form>

    <p><a href="/api/status">JSON API</a></p>
    <p><a href="/protected">Protected page</a></p>
    <form action="/logout" method="post">
      <button>Log out</button>
    </form>
  `);
});

// Demo-only identification: NOT secure authentication.
app.post("/login", (req, res, next) => {
  const name = String(req.body.displayName || "").trim();
  if (!name || name.length > 40) {
    return res.status(400).send("Invalid demo name");
  }
  req.session.regenerate(err => {
    if (err) return next(err);
    req.session.displayName = name;
    req.session.save(err => {
      if (err) return next(err);
      res.redirect("/");
    });
  });
});

app.get("/protected", (req, res) => {
  if (!req.session.displayName) {
    return res.status(401).send("Please enter the demo first");
  }
  res.type("text/plain").send("Protected demonstration: hello " +
           req.session.displayName);
});

app.get("/api/status", (req, res) => {
  res.json({
    hasDemoSession: Boolean(req.session.displayName),
    displayName: req.session.displayName || null
  });
});

app.post("/logout", (req, res, next) => {
  req.session.destroy(err => {
    if (err) return next(err);
    res.clearCookie("www_demo_sid", { path: "/" });
    res.redirect("/");
  });
});

app.listen(PORT, "127.0.0.1", () => {
  console.log("Open http://localhost:" + PORT);
});

Step 3: run and inspect

node server.js

# Then visit:
http://localhost:3000/
  1. Before entering a demo name, open /protected and observe status 401.
  2. Enter a harmless name. The session middleware creates a server-side session and issues a cookie.
  3. Open /protected again. It now allows the demo session.
  4. Inspect Chrome DevTools → Application → Cookies. Notice that a real HttpOnly session cookie is not readable through document.cookie.
  5. Restart the server. The in-memory session store loses its data; the old browser cookie alone is not enough to restore server state.
  6. Try logout and observe server session invalidation.
Do not publish this as a production login system. This sample deliberately lets anyone claim any display name, uses an in-memory session store, and uses secure:false only because the local demonstration is served via HTTP. A real application needs authenticated identity checking, HTTPS with secure cookies, persistent session storage, CSRF protection, proper secret management, rate limiting, access control and deployment-specific proxy configuration.

29. Test your understanding — 25 questions with explanations

Try each question before expanding its answer.

1. What does WWW stand for?

World Wide Web: a system of linked web resources accessible using web technologies.

2. Are the Internet and the Web identical?

No. The Internet is networking infrastructure; the Web is an information and application system built on it.

3. Must every website start with www?

No. “www” is a conventional hostname label/subdomain, not a requirement of the Web.

4. Which three early concepts helped define the Web?

URL/URI identification, HTTP communication and HTML hypertext documents.

5. What is a client?

Software that requests a service, commonly the browser.

6. What does DNS do?

Provides name resolution and associated records, including mappings to IP addresses.

7. What is the difference between port 443 and /profile?

443 identifies a transport service endpoint; /profile is an application URL path.

8. What does HTML control?

Document structure, content and semantic meaning.

9. What does CSS control?

Visual presentation, styles and layout.

10. What does JavaScript commonly do in browsers?

Handles interaction, DOM changes and API requests, among other tasks.

11. Is GET intended for deleting data?

No. GET is intended to be safe and retrieve resources. Deletion should use an appropriate state-changing operation.

12. What is HTTP status 404?

An HTTP response indicating the requested resource was not found.

13. Does HTTPS guarantee that a website is trustworthy?

No. HTTPS protects the connection; a malicious website may still have a valid certificate.

14. What does HTTP statelessness mean?

Each HTTP request does not automatically carry all preceding request history.

15. How does a server usually remember an authenticated user?

It validates a protected session identifier or other credential sent with later requests.

16. Is a cookie the same as a server-side session?

No. The cookie may carry an identifier; the backend maintains or validates the associated state.

17. Can JavaScript read an HttpOnly cookie with document.cookie?

No. HttpOnly blocks that access.

18. Does localStorage automatically travel with HTTP requests?

No. Application JavaScript must explicitly read and send data if required.

19. Is sessionStorage a login-session manager?

No. It is browser storage associated with an origin/page session; authentication must be enforced independently.

20. What is SameSite intended to influence?

Whether and when cookies are sent in cross-site contexts.

21. What is CSRF?

An attack that tricks an authenticated browser into making unwanted state-changing requests.

22. What is XSS?

Injection of executable script/content into a webpage's trusted context.

23. What does CORS control?

Which cross-origin responses browser scripts may read under the policy; it is not an authentication system.

24. What is an API?

An interface through which software communicates; Web APIs often expose HTTP endpoints.

25. Does cloud computing eliminate physical servers?

No. Cloud services run on real infrastructure owned and operated by someone.
